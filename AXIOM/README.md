# AXIOM — سند طراحی ابرسیستم معاملاتی کوانت (نسخهٔ ۱٫۰)

این پوشه، **مجموعهٔ کامل طراحی سیستم معاملاتی AXIOM** است: یک سیستم معاملاتی کوانتِ تک‌صرافی،
تک‌اپراتور، برای بازار **فیوچرز USDT-M صرافی توبیت**، که از پایه (first principles) و مستقل از هر
پروژهٔ پیشین طراحی شده است.

> **بیانیهٔ عدم‌ارث‌بری:** AXIOM نه نسخهٔ ارتقاءیافته، نه اصلاح‌شده و نه ادامهٔ پروژهٔ `apex_gen5` است.
> هیچ معماری، بخش‌بندی، مدل داده، جریان داده، مجموعه‌پارامتر یا ساختار سندی از آن پروژه وام گرفته
> نشده است. تمام محتوای آن ریپو فقط به‌عنوان *منبع دانش* بررسی شده و در `AX-00` و بند ۶ سند `AX-17`
> دقیقاً ثبت شده است که چه چیزی بررسی، چه چیزی رد و به چه دلیل.

## ۲) جانِ ماجرا: سیستم در یک نگاه

AXIOM یک «ماشین شواهد» است که به یک حساب صرافی وصل می‌شود. زنجیرهٔ کار:

```
دریافت داده (REST/WS) → نوار خام فقط-افزودنی (L0) → دادهٔ پالایش‌شده (L1)
   → ویژگی‌ها و وضعیت (با زمان دسترسی اعلام‌شده) → پیش‌بینی‌های کالیبرهٔ بازده خالص (پس از هزینه)
   → ساخت پرتفوی و حجم تحت سقف‌های سخت → کرنل ریسک پیش‌معاملاتی (وتوی fail-closed)
   → اجرای سفارش با پروتکل عدم‌قطعیت نتیجه → ژورنال فقط-افزودنی → مغایرت‌زدایی با صرافی
   → پایش رانش و تخریب → توقف/تنزل خودکار
```

سه چیز این سیستم را از یک رباتِ سیگنال‌فروش جدا می‌کند:

1. **هیچ عددی بدون منشأ وارد سیستم نمی‌شود.** هر پارامتر یکی از چهار کلاس منشأ دارد:
   `[V]` واقعیتِ صرافی (در زمان اجرا از خود صرافی خوانده می‌شود، هرگز هاردکد نمی‌شود)،
   `[D]` مشتق‌شده با فرمول مستند، `[C]` کالیبره‌شده با یک رویهٔ نام‌دار و آزمون پذیرش،
   `[O]` سیاست مالک در یک محدودهٔ مجاز. (قانون `AX-01` بند ۵؛ جدول کامل `AX-15`)
2. **معامله فقط وقتی رخ می‌دهد که کرانِ پایینِ سودِ خالص، هزینهٔ تخمین‌زده‌شده را با حاشیهٔ اطمینان بپوشاند.**
   سیگنال خام هرگز مجوز معامله نیست. (اصل A1 در `AX-06` بند ۷ و `AX-08` بند ۳٫۴)
3. **هر «نمی‌دانم» یک رویه دارد، نه یک حدس.** برای کدهای خطای صرافی، کارایی سخت‌افزار و توزیع هزینهٔ
   اجرا «حدس» وجود ندارد؛ یک آزمون کاوشگر با معیار پذیرش و رفتار fail-closed تعریف شده است.
   (`AX-02` بند ۱۰، `AX-12` بند ۲، `AX-14` بند ۶، `AX-17` بند ۴)

## ۳) محدودهٔ صریح (آنچه AXIOM انجام نمی‌دهد و چرا)

- **HFT / مارکت‌میکینگ / آربیتراژ تأخیر:** مسیر اجرا REST عمومی است و تأخیر واقعی ۱۰²–۱۰³ میلی‌ثانیه
  است؛ هر آلفایی که در این مقیاس معنا نداشته باشد — یعنی افق کمتر از ۱۵ دقیقه — **حذف** شده است.
  این محدودیت از فیزیک مسیر اجرا می‌آید، نه از سلیقه (اصل A6، ADR-007).
- **چند صرافی / سواپ / آپشن / کپی‌تریدینگ:** محدودهٔ مالک، صرافی توبیت و فیوچرز USDT-M است (ADR-001).
  دادهٔ صرافی‌های دیگر فقط به‌عنوان *زمینهٔ رژیم* و تحت شرط‌های ADR-011 مجاز است.
- **خودتغییریِ زندهٔ پارامترها و ریسک:** ممنوع؛ مسیر تغییر، نردبان ارتقاء + کنترل دوگانه است. بدون
  پارامتر فریزشده، «مهارت» از «شانس» قابل تفکیک نیست (اصل A9، ADR-021).
- **وعدهٔ سود:** این اسناد دربارهٔ کیفیتِ *فرآیند، شواهد و ایمنی* هستند، نه دربارهٔ سطح بازده.

## ۵) قراردادهای ماشین‌خوان (`contracts/`)

این بخش، اسناد را از «متن» به «قرارداد قابل بررسی» تبدیل می‌کند:

```bash
python3 contracts/build_registry.py --check     # جدول پارامترها با فایل‌های تولیدشده هم‌خوان است؟
python3 - <<'P'                                  # DDL روی یک پایگاه‌دادهٔ موقت اجرا و قفل فقط-افزودنی ژورنال آزمون می‌شود
import sqlite3,pathlib; sqlite3.connect(':memory:').executescript(pathlib.Path('contracts/sql/schema.sql').read_text())
P
```

- `config.default.yaml` — تمام کلیدها با شناسهٔ پارامتر، کلاس منشأ و ارجاع کالیبراسیون در کامنت.
  کلیدهای `[O]` **عمداً `null`** هستند تا سیستم تا اعلام رسمی مالک روشن نشود.
- `registry.json` — رجیستر ماشین‌خوان (شناسه، کلاس، واحد، بازه، ارجاع کالیبراسیون، ورودی مالک).
- `sql/schema.sql` — ۵۰ جدول L0–L2 و کنترل، ۵ نما برای رابط اپراتور، و **تریگرهایی که فقط-افزودنی بودن
  ژورنال را در سطح پایگاه‌داده اجبار می‌کنند** (نه فقط در متن).
- `schemas/*.json` — اسکیمای JSON برای بارها، معاملات، دفتر سفارش، سفارش‌ها، پر شدن‌ها، پیش‌بینی‌ها،
  هدف‌ها، تصمیم‌ها، رویداد ژورنال، پروفایل صرافی، کارت مدل و رکورد دروازه.

سیستم بدون این یازده ورودی در حالت `OFF` می‌ماند و **هیچ سفارشی** ارسال نمی‌کند (رفتار fail-closed
طراحی‌شده، نه باگ):

| شناسه | تصمیم مالک |
|---|---|
| `OI-RISK-01` | ریسک هر معامله (`R`) نسبت به سرمایه |
| `OI-RISK-02` | حداکثر افت سرمایه‌ای که سیستم باید در آن به‌طور خودکار ریسک را قطع کند |
| `OI-RISK-03` | هدف نوسان، افق‌های زمانی مجاز، سقف ناخالص/خالص/بتا، سقف گردش، حاشیهٔ اطمینان سود در برابر هزینه |
| `OI-RISK-04` | سقف ضرر روزانه |
| `OI-RISK-05` | چند برابر بودن بدترین زیان شکاف (gap) نسبت به `R`، کسر کلی، سخت‌گیری آماری ارتقاء، سقف آزمون ماهانه |
| `OI-CAP-01` | حداکثر تعداد نماد قابل معامله و حداکثر پوزیشن باز |
| `OI-CAP-02` | نگهداری داده، بودجهٔ فضای ذخیره‌سازی، محل و فاصلهٔ پشتیبان‌گیری |
| `OI-OPS-01` | توپولوژی استقرار (تک‌دستگاه / لبه+محاسبه / سرور) و دستگاه اجرا |
| `OI-OPS-02` | کانال و مقصد اطلاع‌رسانی هشدارهای SEV-1/2 |
| `OI-OPS-03` | تعهد پایش (روزانه/هفتگی)، تایمر ضربان اپراتور، مدت‌زمان‌های نردبان |
| `OI-GOV-01` | اختیار مسلح‌سازی، ارتقاء و «قطع سخت»؛ وجود یا نبود نفر دوم برای کنترل دوگانه |

## ۷) وضعیت و گام بعدی

- **نسخهٔ اسناد: `1.0` (کامل).** هر ۱۹ سند (`AX-00`…`AX-18`) و مجموعهٔ `contracts/` نوشته شده‌اند؛
  بررسی خودکار پارامترها و DDL سبز است؛ عبارت‌های مبهم ممنوع (`TBD`, «بعداً تصمیم گرفته می‌شود»)
  با lint سند `T-DOC-001` رد می‌شوند.
- **گام بعدی مالک:** تکمیل یازده ورودی بند ۶ (به‌ویژه `OI-RISK-01/02/03` که کل ریاضیات اندازهٔ پوزیشن
  به آن‌ها آویزان است) و تصمیم `OI-OPS-01` دربارهٔ دستگاه اجرا.
- **گام بعدی تیم فنی (به ترتیب):** `WP-000` اسکلت مخزن → `WP-010..015` هارنس تأیید صرافی (VCH) →
  کالکتورهای داده (`WS-2`) و شروع بی‌درنگ گردآوری تاریخ → بنچمارک‌های سخت‌افزار `BENCH-01..10` →
  برش عمودی «فقط-رد» (`AX-16` بند ۷) در حالت `PAPER`.
- **بدون دروازهٔ `G6` و بدون تأیید کتبی مالک، مسیر `MICRO_LIVE`/`LIVE` در کد قفل است** — حتی اگر تمام
  آزمون‌ها و شبیه‌سازی‌ها موفق باشند. هیچ سند، شبیه‌سازی یا آزمون تاریخی مجوز معاملهٔ زنده نیست.

منابع رسمی به‌کاررفته برای واقعیت‌های صرافی (تاریخ بررسی: ۲۰۲۶-۱۰-۱۲): مستندات رسمی
`api-docs.toobit.com` و کیت رسمی `github.com/toobit-docs/agent-kit` در کامیت `2ee2d6b5…`.
هر واقعیت صرافی در `AX-02` با برچسب `[V-DOC]`/`[V-KIT]`/`[V-PROBE]` و تاریخ مشخص شده و پیش از
استفادهٔ زنده باید با هارنس کاوشگر بازتأیید شود؛ تا آن زمان رفتار سیستم fail-closed است.
